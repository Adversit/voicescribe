# 界面卡顿治理执行计划（仅规划，不执行）

## 1. 目标与范围
- 目标：解决“某个页面加载导致全应用卡死”的问题，确保页面切换与录音流程可并行响应。
- 范围：`frontend` 渲染层、`electron` 主进程 IPC、后端请求触发策略。
- 非目标：本计划阶段不改识别模型精度，不调整业务功能语义。

## 2. 问题假设
- UI 卡顿主要来自以下几类阻塞：
- 页面切换时触发多个重请求（健康检查、模型列表、说话人列表）并发挤占事件循环。
- 渲染层高频状态更新（录音波形、partial 日志）引发过度重渲染。
- Electron 主进程存在同步 I/O 或长耗时 IPC handler，阻塞窗口消息循环。
- 请求无并发控制与取消，页面离开后旧请求仍回写状态。

## 3. 执行原则
- 先“去阻塞”，后“加缓存”。
- 先“可观测”，再“优化”。
- 每一步可独立回滚，避免一次性大改。

## 4. 分阶段计划

## Phase A：观测与基线（1 天）
- 增加前端性能埋点：
- 页面切换耗时、首次可交互时间、接口请求时长、渲染帧丢失率（近似）。
- 增加 Electron 埋点：
- IPC handler 执行耗时日志（>100ms 告警）。
- 产出基线报告：
- 卡顿复现步骤、慢点 TopN、CPU 峰值与频率。

交付物：
- `docs/perf-baseline.md`（建议新增）
- 可复现脚本（页面切换 + 录音 + 模型加载）

## Phase B：渲染层去阻塞（1-2 天）
- 页面级请求隔离：
- 各设置页仅在“进入该页”发请求，离开即取消（AbortController）。
- 禁止跨页面共享 loading 锁：
- 每个模块独立 `isLoading/error`。
- 高频更新节流：
- 波形更新从 100ms 调整为可配置节流（如 150-200ms）。
- partial 文本渲染节流（如 300-500ms 合并更新）。
- 组件懒加载：
- 设置页子面板按需加载，避免初次挂载全部执行 effect。

验收：
- 页面切换时，其他页面操作不冻结。
- 录音中打开设置页不出现明显卡死（>1s 无响应）。

## Phase C：请求并发治理（1 天）
- 统一请求层增加“同类请求单飞”：
- `engines/models/speakers/health` 同时只允许一个 in-flight。
- 加入请求取消：
- 切页、弹窗关闭时取消旧请求，禁止过期回写。
- 轮询限频：
- 健康检查 2-5s；下载进度 1-2s；空闲页停止轮询。

验收：
- 网络抖动下页面仍可交互。
- 同一接口不会出现请求风暴。

## Phase D：Electron 主进程瘦身（1 天）
- 排查并替换同步 I/O：
- `fs.readFileSync/writeFileSync` 在高频路径改异步。
- IPC handler 短路径返回：
- 长任务改“启动任务 + 事件推送进度”。
- 分离阻塞任务：
- 必要时将重 CPU 工作迁移到子进程/worker。

验收：
- 主进程日志无持续 >100ms 阻塞 handler。
- 托盘、快捷键、窗口响应不受后台任务影响。

## Phase E：轻缓存（可选，0.5-1 天）
- 仅缓存稳定数据：
- `settings`（会话级）、`engines`（TTL 30s）、`speakers`（TTL 10-30s）。
- 不缓存强实时数据：
- 下载进度、录音状态、partial 文本仅做节流，不做长缓存。
- 增量刷新：
- 命中缓存先渲染，再后台静默刷新。

验收：
- 重复进入页面的等待时间显著下降。
- 数据一致性可接受，无明显陈旧误导。

## 5. 任务拆解（建议顺序）
1. 建立埋点与慢日志（A）
2. 设置页请求隔离 + 取消（B）
3. 波形与 partial 渲染节流（B）
4. 请求单飞与轮询限频（C）
5. 主进程同步 I/O 清理（D）
6. 引入轻缓存（E，可选）

## 6. 风险与回滚
- 风险：节流过度导致“看起来慢”。
- 方案：阈值可配置，保留开关。
- 风险：请求取消导致状态丢失。
- 方案：仅取消可重试查询类请求，不取消关键提交。
- 回滚策略：
- 每个 Phase 独立提交；出现回归按 Phase 回退。

## 7. 验收指标（建议）
- 页面切换可交互时间：P95 < 300ms
- 设置页接口失败率：< 1%
- 录音中打开设置页冻结时长：P95 < 200ms
- 主进程阻塞 handler（>100ms）次数：下降 80%+

## 8. 本次结论
- 本文档为执行计划，当前不执行任何代码改动。
- 待你确认后，按 Phase A -> E 逐步实施。
