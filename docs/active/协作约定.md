# 协作约定

更新时间：2026-03-31
适用分支：`0325main`

## 1. 目标

当前仓库已把 Phase 1 的计划、spec、测试和专题文档整体归档。
本文件只保留持续有效的协作规则；阶段状态、归档入口和下一步范围统一看 [2026-03-31-phase-status.md](D:\learn\AIGC\voicescribe\0324\voicescribe\docs\active\2026-03-31-phase-status.md)。

## 2. Source of Truth

优先级从高到低如下：
1. [2026-03-31-phase-status.md](D:\learn\AIGC\voicescribe\0324\voicescribe\docs\active\2026-03-31-phase-status.md)
2. 当前任务直接相关的归档文档
3. 当前代码实现

如果当前状态文档、归档 spec、代码三者冲突：
- 先以当前状态文档定义的阶段口径为准
- 再看对应归档专题或 Phase 1 文档
- 最后再修代码

## 3. 固定流程

后续默认按这个顺序执行：
1. 先更新相关文档
2. 再改代码
3. 再执行我能做的测试
4. 先把测试结果写进对应测试文档
5. 再由你做人肉验收
6. 验收通过后再提交和 push

如果是纯文档任务，可以停在第 1 步。
如果是 Phase 1 尾项修复，也不能跳过测试记录。

## 4. 完成定义

以后不再把“构建通过”直接说成“完成”。
默认只有以下条件同时满足，才可以说“这一项完成”：
- 对应文档已同步
- 代码已落地
- 我能做的测试已经执行
- 测试结果已写入对应测试文档
- 需要人工验收的部分，已经明确标出“待人工验收”

## 5. 测试与 Bug 记录规则

### 5.1 硬规则
没有写进对应测试文档的，一律视为没测。

### 5.2 Phase 1 尾项
如果工作仍属于 Phase 1 收口或补验收：
- 测试结果写入 [第一阶段测试.md](D:\learn\AIGC\voicescribe\0324\voicescribe\docs\archive\phase1\第一阶段测试.md)
- 新 bug 写入 [2026-03-25-session-bug-log.md](D:\learn\AIGC\voicescribe\0324\voicescribe\docs\archive\phase1\2026-03-25-session-bug-log.md)

### 5.3 新阶段
如果已经进入新阶段：
- 在 `docs/active/` 新建该阶段自己的测试文档和 bug 文档
- 不继续把新阶段规划混写进已归档的一阶段文档

## 6. UI 任务规则

UI 任务默认遵循以下约束：
- 不自由发挥，先对照 `app/` 原生界面
- 先更新 spec 或状态文档，再改界面
- 优先保证结构和体验一致，而不是先追求“好看”
- 单层主表面优先，不做 `outer shell + inner panel`
- 尽量单屏可见；允许滚动，但不要默认依赖整页滚动
- 页面布局优先贴近原生设置页，不做 dashboard 风格

## 7. 什么时候我必须停下来问你

遇到以下情况，我不应继续猜：
- 当前状态文档和归档 spec 含义冲突
- UI 方向存在明显主观判断
- 代码能跑，但体验是否符合预期无法靠测试确认
- 修复需要改动产品口径，而不仅是实现细节
- 一轮修复后你再次指出“方向就不对”

## 8. 提交规则

- 默认在 `0325main` 上工作
- 未经你确认，不提前 push
- 提交前先说明这轮改了什么、测了什么
- 不提交 `docs/` 里的临时截图、参考图片或无关文件，除非你明确要求

## 9. 编码与文档规则

- 中文源码和中文文档统一用 UTF-8
- 当前默认是 Windows PowerShell 环境，不是 WSL / Linux / macOS；终端显示乱码时，不直接判定文件损坏，要先做 UTF-8 实读校验
- 通过命令行写入含中文的源码或文档时，不把原始中文直接塞进 PowerShell 命令串；优先使用 ASCII 安全脚本、Unicode 转义或其他可控方式写回 UTF-8
- 文档乱码修复后，需要重新检查文件内容，而不是只看终端输出
- 新增或重写中文文件后，至少做一次 UTF-8 实读验证；确认不是 `?`、替换字符或控制台误显

## 10. 协作目标

后续合作的目标不是“更快给出一个答案”，而是：
- 更少反复
- 更少猜测
- 更少自由发挥
- 更稳定地按文档和验收标准推进
