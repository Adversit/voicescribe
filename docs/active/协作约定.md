# 协作约定

更新时间：2026-03-28
适用分支：`0325main`

## 1. 目标

本文档用于约束后续协作方式，减少“我以为已经完成、你看到的却不是这样”的情况。
后续开发、文档、测试、提交，默认都以本文档为协作规则。

## 2. Source of Truth

优先级从高到低如下：
1. [0325第一阶段改造计划.md](D:\learn\AIGC\voicescribe\0324\voicescribe\docs\active\0325第一阶段改造计划.md)
2. [2026-03-25-voicescribe-windows-spec.md](D:\learn\AIGC\voicescribe\0324\voicescribe\docs\active\2026-03-25-voicescribe-windows-spec.md)
3. [2026-03-26-implementation-gap-checklist.md](D:\learn\AIGC\voicescribe\0324\voicescribe\docs\active\2026-03-26-implementation-gap-checklist.md)
4. 当前代码实现

如果 `plan`、`spec`、代码三者冲突：
- 先以 `plan` 为准
- 再修正 `spec`
- 最后修代码

## 3. 固定流程

后续默认按这个顺序执行：
1. 先更新相关文档
2. 再更新差距清单
3. 再改代码
4. 再执行我能做的测试
5. 把测试结果写入测试文档
6. 再由你做人肉验收
7. 验收通过后再提交和 push

如果是纯文档任务，可以停在第 2 步。
如果是纯代码修复，也不能跳过文档更新和测试记录。

## 4. 完成定义

以后不再把“构建通过”直接说成“完成”。
默认只有以下条件同时满足，才可以说“这一项完成”：
- 对应 `plan/spec/checklist` 已同步
- 代码已落地
- 我能做的测试已经执行
- 测试结果已写入 [第一阶段测试.md](D:\learn\AIGC\voicescribe\0324\voicescribe\docs\active\第一阶段测试.md)
- 需要人工验收的部分，已经明确标出“待人工验收”

## 5. 测试规则

### 5.1 硬规则
没有写进 [第一阶段测试.md](D:\learn\AIGC\voicescribe\0324\voicescribe\docs\active\第一阶段测试.md) 的，一律视为没测。

### 5.2 我负责的测试
我默认负责：
- 构建测试
- 启动链测试
- 后端接口测试
- 代码层回归测试
- 能自动化执行的主链路验证

### 5.3 你负责的测试
你默认负责：
- 热键真实桌面行为
- 麦克风录音体感
- 文本注入到外部应用
- 托盘图标与托盘菜单真实体验
- 窗口观感、比例、布局体验
- 安装包安装后的真实使用体验

## 6. Bug 记录规则

如果出现“这轮没有一次做对”的问题：
- 先修问题
- 再把原因写进 [2026-03-25-session-bug-log.md](D:\learn\AIGC\voicescribe\0324\voicescribe\docs\active\2026-03-25-session-bug-log.md)
- 如果问题暴露出 spec 缺失，再同步补 spec

## 7. UI 任务规则

UI 任务默认遵循以下约束：
- 不自由发挥，先对照 `app/` 原生界面
- 先更新 spec 和 UI 计划文档，再改界面
- 优先保证结构和体验一致，而不是先追求“好看”
- 单层主表面优先，不做 `outer shell + inner panel`
- 尽量单屏可见；允许滚动，但不要默认依赖整页滚动
- 页面布局优先贴近原生设置页，不做 dashboard 风格

## 8. 什么时候我必须停下来问你

遇到以下情况，我不应继续猜：
- `plan` 和 `spec` 含义冲突
- UI 方向存在明显主观判断
- 代码能跑，但体验是否符合预期无法靠测试确认
- 修复需要改动产品口径，而不仅是实现细节
- 一轮修复后你再次指出“方向就不对”

## 9. 提交规则

- 默认在 `0325main` 上工作
- 未经你确认，不提前 push
- 提交前先说明这轮改了什么、测了什么
- 不提交 `docs/` 里的临时截图、参考图片或无关文件，除非你明确要求

## 10. 编码与文档规则

- 中文源码和中文文档统一用 UTF-8
- 当前默认是 Windows PowerShell 环境，不是 WSL / Linux / macOS；终端显示乱码时，不直接判定文件损坏，要先做 UTF-8 实读校验
- 通过命令行写入含中文的源码或文档时，不把原始中文直接塞进 PowerShell 命令串；优先使用 ASCII 安全脚本、Unicode 转义或其他可控方式写回 UTF-8
- 文档乱码修复后，需要重新检查文件内容，而不是只看终端输出
- 新增或重写中文文件后，至少做一次 UTF-8 实读验证；确认不是 `?`、替换字符或控制台误显
## 11. 协作目标

后续合作的目标不是“更快给出一个答案”，而是：
- 更少反复
- 更少猜测
- 更少自由发挥
- 更稳定地按文档和验收标准推进
